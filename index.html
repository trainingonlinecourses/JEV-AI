The mismatch

LLMs write text for humans. Your code needs decisions.

Every "classification" you run through a chat model is really a text-generation task you then coerce, parse, validate and retry back into a value. TypeSafe flips it: Jev is trained to output calibrated decisions — typed values with probability distributions — not sentences. That's the whole idea of a System One model: fast, structured judgment software can consume directly.

Today · text LLM Prompt → prose → parse → pray

  • 1Write a prompt asking GPT‑5.6 / Opus 5 / Gemini 3.1 / Qwen3.8 / Kimi / DeepSeek to "respond with strict JSON".
  • 2Pay for tokens — including prose, apologies, markdown fences and reasoning you never wanted. Output tokens are the expensive side ($3.75–$50 / 1M).
  • 3Parse & validate — json.loads, schema checks, enum guards, type coercion.
  • 4Handle failures — ~5–10% of calls need retries or a repair prompt. 2× tokens, 2× latency.
  • 5Trust a single value — "urgency": 4 arrives with no probability, no confidence, nothing to route on.

System One · Jev Questions → typed answers → code

  • 1Declare typed questions — Choice, Score, Noul — against a state object. No prompt engineering.
  • 2One call, parallel evaluation — every question judged independently against the same state. Adding questions barely moves latency.
  • 3Structured results, guaranteed — the answer is the schema. Nothing to parse, nothing to repair.
  • 4Probabilities + confidence — 0.61 / 0.24 / 0.09 / 0.06 and confidence: 0.82 you can branch, sort and escalate on.
  • 5~172 ms median — fast enough to sit inline in front of every other model in your stack.
Three AI primitives

Modular, composable, structured, reliable, fast.

All three question types can be mixed in a single API call. Each is evaluated in parallel and in isolation — so adding more questions never creates context rot. Keep each question atomic (a "gut-check" a knowledgeable human could make in seconds), then compose the judgment in your code, with weights you control.

Choice

pick one option from a list

"What is the primary intent of this ticket?" → returns the selected option, a probability for every option, and confidence.

choiceprobabilities{}confidence
{
  "choice": "billing",
  "probabilities": {
    "billing": 0.61, "churn_risk": 0.24,
    "bug_report": 0.09, "feature_request": 0.06
  },
  "confidence": 0.82
}

Score

rate the state on an ordered rubric

"How urgent is this ticket?" with descriptive levels → returns the score, the full distribution over levels, and confidence.

scoreprobabilities{}confidence
{
  "score": 4,
  "probabilities": {
    "1": 0.01, "2": 0.06, "3": 0.25,
    "4": 0.47, "5": 0.21
  },
  "confidence": 0.74
}

Noul

is this statement true? → 0–1

"Does this ticket contain PII?" → returns the probability that the answer is yes. The perfect cheap boolean gate in front of expensive logic.

noul ∈ [0, 1]
{
  "noul": 0.83
}
// if (answer.noul > 0.7) redactPII(ticket);
Composite scoring: instead of asking a frontier model to "rate this startup pitch" (one blob judgment), ask Jev separately about market size, technical feasibility and differentiation — then combine with your own formula. When priorities shift, change a coefficient in code, not a prompt.

quickstart.py — sync, async & retries
from typesafe import TypeSafeClient, AsyncTypeSafeClient, RetryPolicy

client = TypeSafeClient(
    retry_policy=RetryPolicy(attempts=3, backoff=0.4),   # retryable statuses + backoff headers handled
)

resp = client.evaluate(
    state={"ticket": ticket},
    questions=[
        {"id": "intent", "type": "choice",
         "question": "Primary intent of this ticket?",
         "options": ["billing", "bug_report", "feature_request", "churn_risk"]},
        {"id": "urgency", "type": "score",
         "question": "How urgent is this ticket?",
         "levels": ["1 — can wait", "2 — this week", "3 — today", "4 — hours", "5 — drop everything"]},
        {"id": "contains_pii", "type": "noul",
         "question": "Does this ticket contain PII?"},
    ],
)

intent = resp.answers["intent"]           # typed object
print(intent.choice, intent.confidence)   # "billing" 0.82
print(resp.answers["urgency"].score)      # 4
print(resp.usage)                         # token usage per question

models = client.list_models()             # discover available System One models

# async flavor for high-throughput services:
# aclient = AsyncTypeSafeClient(); await aclient.evaluate(...)

open_models_triage.py · Qwen3.8-Max $2/$6 · Kimi K2.6 $0.60/$2.50 · DeepSeek V4 Flash $0.14/$0.28 off-peak
import json
from openai import OpenAI
from pydantic import BaseModel, ValidationError
from typing import Literal

class TicketDecision(BaseModel):
    intent: Literal["billing", "bug_report", "feature_request", "churn_risk"]
    urgency: int
    contains_pii: bool

# DeepSeek: https://api.deepseek.com/v1   ·   Qwen: dashscope   ·   Kimi: api.moonshot.ai
client = OpenAI(base_url=BASE_URL, api_key=KEY)

SYSTEM = ("You are a strict ticket classifier. Reply with JSON only: "
          '{"intent": "billing|bug_report|feature_request|churn_risk", '
          '"urgency": 1-5, "contains_pii": true|false}. No other text.')

def decide(state_json, attempts=3):
    for attempt in range(attempts):
        r = client.chat.completions.create(
            model=MODEL,                     # "deepseek-v4-flash" | "qwen3.8-max" | "kimi-k2.6"
            messages=[{"role": "system", "content": SYSTEM},
                      {"role": "user", "content": state_json}],
            response_format={"type": "json_object"},
            temperature=0.0,
        )
        try:
            return TicketDecision.model_validate_json(r.choices[0].message.content)
        except (ValidationError, json.JSONDecodeError):
            continue                          # every retry re-bills all tokens
    raise RuntimeError("model could not produce a valid decision")

Confidence & state

  
Confidence: the second axis your code has been missing.

  
Probability tells you what the model chose and how the remaining mass is spread. Confidence tells you how strongly the model stands behind the answer — the signal that decides whether your system should act automatically, act with an audit trail, or escalate.


  

    

      
Probability
distribution over the options

      
"billing 0.61 · churn_risk 0.24" — useful for sorting queues, weighing composite scores, and detecting close calls between two options.

    

    

      
Confidence
how sure the model is · 0–1

      
"confidence 0.82" — useful for gating: act, sample-audit, or escalate. Choice and Score return it directly; Noul's probability is itself the gate.

    

  


  

    
Confidence
What your system should do
Code

    
≥ 0.85
Act automatically. Route, tag, approve — fully deterministic path, no human, no frontier model.
act(answer)

    
0.60 – 0.84
Act + audit. Proceed, but sample a percentage into a review queue; track drift over time.
act(answer); audit(sample=0.1)

    
0.30 – 0.59
Escalate to a frontier model. Send the state to GPT‑5.6 / Opus 5 / Gemini 3.1 for deep reasoning — only now.
escalate(state, "claude-opus-5")

    
< 0.30
Stop. Ask a human — or re-ask as smaller, better-scoped questions with clearer instructions.
queue_for_human(state)

  


  

    

      
Architectural rule of thumb

      
gating.py — confidence × risk
def threshold_for(risk: str) -> float:
    return {"low": 0.60, "medium": 0.75, "high": 0.90}[risk]

ans = jev.evaluate(state=s, questions=[INTENT, URGENCY, PII])
conf = ans.answers["intent"].confidence
risk = "high" if involves_payments(s) else "low"

if conf >= threshold_for(risk):
    auto_act(ans)                       # most traffic ends here
else:
    escalate(s, model="gpt-5.6-sol")    # pay frontier prices ONLY for doubt


      
Raise the bar with risk. Tagging a ticket at 0.7 confidence is fine. Refunding $4,800 at 0.7 is not — high-stakes actions get a higher threshold, which simply shifts more traffic to the escalation branch.

Architectural patterns

  
Keep code in control. Give the model narrow decisions.

  

    
01
Confidence-gated routing
The answer tells you what; confidence tells you whether to act. High confidence → automatic path. Low confidence → frontier model, human review, or a second, narrower question.

    
02
Composite scoring
Never ask one big "rate this" question. Ask atomic Score questions per dimension, combine with weights in your code. Change priorities by changing a coefficient, not a prompt.

    
03
Intent routing
Classify every incoming request in ~172 ms and route it to the optimal handler: deterministic logic, GPT‑5.6 Luna, DeepSeek V4 Flash, a specialist model, or a human. The router costs fractions of a cent.

    
04
Speculative fan-out
Send many questions in one call — including speculative ones ("would this user churn?", "does this need legal?"). Adding questions barely changes latency; your code decides which answers matter.
